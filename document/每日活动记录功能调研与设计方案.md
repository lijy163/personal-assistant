# 「每日活动记录」功能调研与设计方案

> 版本：v1.0 ｜ 日期：2026-10-13
> 范围：项目现状梳理 + 开源同类调研 + 方案选型（集成 vs 新建）+ 落地建议
> 结论先行：**新建独立后端模块 `activity` + 独立前端页面 `/activity`，同时在仪表盘和全局搜索做两处轻量挂载**。理由见第五章。

## 一、项目现状梳理

### 1.1 整体架构

`personal-assistant` 是一个「四端一体」的个人自托管系统，代码仓库内并列四个子项目：

| 子项目 | 角色 | 技术栈 |
| --- | --- | --- |
| `personal-assistant-server` | 主后端，全部业务能力 | Spring Boot 3.3.6 / Java 17 |
| `personal-assistant-web` | 主前端（PC + 移动 PWA） | Vue 3 + Vite 6 + TypeScript |
| `personal-assistant-agent` | 本机 Codex 任务执行器（主动拉取任务） | Node.js ≥20，零第三方依赖 |
| `rain7-blog` | 独立 Astro 博客站（内容仍由主后端提供） | Astro 5 + React 19 islands |

另有 `deploy/`（Docker Compose）、`document/`（设计与需求文档）、`scripts/`（开发日志推送脚本）。

### 1.2 技术栈总览

**后端**

- 框架：Spring Boot 3.3.6，Java 17，Maven
- 持久层：MyBatis-Plus 3.5.9 + PostgreSQL
- 数据库版本管理：Liquibase（当前 45 个 changelog，`001` ~ `045`）
- 定时调度：Quartz（JDBC JobStore，`QRTZ_*` 标准表）
- 认证：Spring Security + JJWT 0.12.6（JWT，无状态）
- 其他：Apache POI 5.3.0（Excel）、springdoc-openapi 2.6.0（Swagger UI）、Lombok
- 端口 8080，默认 profile `local`（本地 PostgreSQL 5433）

**前端**

- Vue 3.5 + TypeScript 5.6 + Vite 6 + Element Plus 2.9
- Vue Router 4（嵌套布局）、Pinia（**已注册但实际未使用任何 store**）、Axios 1.7
- ECharts 5.6 + `BaseChart.vue` 封装、markdown-it + DOMPurify
- PWA（Service Worker + manifest + 移动端底部导航）
- 开发代理：`/api` → `http://localhost:8080`

### 1.4 前端页面与菜单结构

主布局 `layouts/ResponsiveAppLayout.vue`（PC 侧边栏 232px + 移动端抽屉 + 底部导航）。侧边栏菜单在 `layouts/AppNavigation.vue` 中**硬编码**，共 5 组：

1. **首页** — 每日驾驶舱、统一收件箱、收件箱整理
2. **事务与生活** — 统一日历、项目排期、生活事项、工作事项、提醒中心、自动化规则、习惯/联系人/资产
3. **知识沉淀** — 知识库与 AI、学习计划/记录/总结/成长看板、开发记录、博客管理、两个外链
4. **财务市场** — 个人账单、预算与净资产、股票关注、交易复盘、交易规则、次日计划、金价关注、自动报告
5. **系统管理** — 安全审计、调度管理、推送令牌、远程 Codex、系统设置、部署运维

菜单与路由是**两处独立维护**：`router/index.ts` 定义路由，`AppNavigation.vue` 定义菜单项 + `groupRoutes` 分组映射（用于高亮、展开记忆、路由预加载）。**新增页面需要同时改这两处。**

### 1.5 关键基础设施（新功能必须对齐的约定）

- **统一响应体**：`ApiResponse<T>(code, message, data, traceId)`，成功码 `SUCCESS`；前端拦截器已剥离外层，业务层写 `(await xxx()).data`
- **异常**：`BusinessException(ErrorCode)` + `GlobalExceptionHandler`，不要自己 try/catch 成 500
- **当前用户**：`SecurityContextHelper.currentUserId()`，Controller 内以私有 `uid()` 封装
- **鉴权**：JWT 过滤器链，`/api/**` 默认需登录，公开路径在 `SecurityConfig.PUBLIC_PATHS` 白名单
- **建表**：新增 Liquibase changelog（下一个编号 `046`）并在 `db.changelog-master.yaml` include，**不修改历史 changelog**
- **表约定**：`id bigserial PK`、所有业务表带 `user_id` 做隔离、时间用 `timestamp`、`created_at`/`updated_at`
- **前端约定**：每个业务域一个 `api/xxx.ts`；页面用 Element Plus；桌面 `el-table` + 移动端卡片双套模板（见 `InboxView.vue` / `TaskListView.vue`）

### 1.6 与「记录」相关的既有能力盘点（避免重复造轮子）

| 既有能力 | 表 | 语义与生命周期 | 与「每日活动记录」的关系 |
| --- | --- | --- | --- |
| 快捷记录 | `quick_note` | `PENDING → ARCHIVED / CONVERTED` | 同样是**待整理**语义，终点是"被转走" |
| 统一收件箱 | `inbox_item` | `PENDING → CONFIRMED → CONVERTED`，含 `converted_type/converted_id/conversion_params` | **核心是"待归类素材"**，终点是"转成任务/提醒/消费/学习" |
| 开发记录 | `dev_log` | 终态记录，含 commit/分支/技术决策 | 领域限定在开发，不通用 |
| 学习记录 | `learning_record` | 终态记录，挂在 learning_plan 下 | 领域限定在学习 |
| 习惯打卡 | `habit_checkin` | `(user_id, habit_id, checkin_date)` 唯一 | 只记"做没做"，不记"做了什么" |
| 事项 | `task_item` | 有状态机（NOT_STARTED → … → DONE） | 是"计划"，不是"已发生的事实" |

**关键结论：系统里没有任何一张表是「已发生事实的通用时间线」。** 最接近的是 `quick_note` 和 `inbox_item`，但二者都带"待整理/待转换"状态机，语义是"入口"而非"档案"。这是本次需求的真实空白区（`document/个人系统待开发规划.md` 中也无对应规划）。

## 二、需求定义

**目标**：记录"我每天做了什么事情"。

**用户明确约束**：

- ✅ 随时记录（低摩擦、随开随记）
- ✅ 如实记录（不强制结构化、不强制分类、不做价值判断）
- ✅ 只聚焦记录本身
- ❌ 暂不做分析、统计洞察、任务联动、AI 归类等扩展

**由此推导出的设计红线**：

| 红线 | 说明 |
| --- | --- |
| 不做状态机 | 记录写进去就是"已完成的事实"，不存在"待确认/待转换" |
| 不强制字段 | 只有"内容"是必填，分类/标签/时间都是可选补充 |
| 必须能按天回溯 | 记录天然是时间序列，要能"翻到某一天看那天干了什么" |
| 时间归属与时间戳分离 | 允许补记（今天补记昨天的事），所以要区分「归属日期」与「发生时刻」 |
| 录入路径最短 | 从打开到写入 ≤ 1 次点击 + 1 次输入 |

### 3.2 逐个亮点拆解

#### ① Memos —— 「时间线 + 零门槛捕获」的范式

**功能亮点**

- **Write first**：写一条内容**不需要选标题、不需要选文件夹、不需要选模板**，Markdown 直接发。这是"随时记录"的黄金标准。
- **Timeline 为主视图**：所有记录按时间倒序铺成一条流，不是表格、不是列表卡片，而是"信息流"。
- **日历回溯**：可以直接"回看任何一天"的时间线（day view）。
- **标签 + 筛选 + 保存视图（views）**：用 `#tag` 轻量组织，把常用筛选组合存成"视图"。
- **隐私默认私有**：新记录默认仅自己可见。
- **Web Clipper**：浏览器插件把网页/选区/图片带来源链接直接存进来。

**页面设计可借鉴点**

- 顶部一个**常驻 composer**（不弹窗、不跳页），下方就是时间线 —— 录入与浏览在同一屏内，这是"随时记录"的关键。
- 每条记录卡片很轻：时间戳 + 正文 + 标签，没有多余元信息噪声。
- 日历作为**导航器**（点某天 → 过滤到那天），而不是统计图表。

#### ② ActivityWatch —— 「事实数据模型」的严谨性

**功能亮点**

- 核心模型只有两层：**bucket（数据桶）→ event（事件）**，event 就是 `{ timestamp, duration, data }`。极简且可扩展。
- 所有 watcher（窗口/浏览器/AFK）写入统一 event 流，上层再做聚合。
- **本地优先 + 无遥测**：数据全部留在本机，服务端只提供 REST API。
- 可视化：Timeline（横向时间条带）、Activity grid（类 GitHub 贡献图）。

**可借鉴点**

- **「归属日期」与「事件时刻」分离**的思路，与 event 的 `timestamp` 语义一致 —— 对应本方案 `log_date` + `occurred_at` 双字段。
- 横向时间条带（timeline bar）比表格更适合"一天做了什么"的直觉阅读。

#### ③ Dayflow —— 「回顾面板」的表达力

**功能亮点**

- 把屏幕活动转成**一条时间线**，并生成"昨天亮点 / 今日重点 / 阻塞项"三段式摘要面板。
- **GitHub 风格活动网格（activity grid）**：一眼看到"哪天记了、哪天断了"。

**可借鉴点**

- **活动网格**是"如实记录"的正反馈装置：填满格子本身就是动力，且不需要任何分析功能。
- 三段式（昨日/今日）面板结构，可简化成"今天已经记了 N 条"的轻提示。

#### ④ Traggo —— 「标签即结构」+ 双视图

**功能亮点**

- **没有任务，只有带标签的时间跨度**（`timespan`）。结构完全由标签自定义（`project=xx`、`type=programming`）。
- 同时提供 **list 视图和 calendar 视图**，可切换。
- 可自定义仪表盘图表、多主题。

**可借鉴点**

- **"不给用户预设结构，只给标签"** 与本需求"如实记录"完全同频。分类字段应该是可选补充，而不是必填的下拉框。
- **列表 / 日历双视图切换**是一个低成本、高价值的页面结构。

#### ⑤ Daily You —— 「每日节奏」与离线可靠性

**功能亮点**

- 每天一个入口（"每日记录"），带**随机时间的温和提醒**养成习惯。
- 心情追踪 + 图片 + Markdown。
- **离线优先**（Offline-first）：无网也能写，永远可用。
- 数据导出/迁移，支持从别的 App 导入。

**可借鉴点**

- **离线队列**：本项目已有现成实现（`utils/inboxOfflineQueue.ts` + `InboxView.vue` 的离线分支），可直接复用同一模式 —— 这是移动端"随时记录"的刚需。
- **草稿自动保存**：`InboxView.vue` 已用 `localStorage` 做 draft，可复用。

#### ⑥ jrnl —— 「零摩擦录入」的交互极限

- 命令行一条 `jrnl 今天写了方案` 即完成记录，自动打时间戳、自动归属日期。
- 支持 `@tag`、星标、多日记本。
- 启示：**录入成本必须低到"不需要思考"**，任何必填的额外字段都是摩擦。

### 3.3 借鉴点汇总 → 融入本功能

| 借鉴点 | 来源 | 如何融入「每日活动记录」 | 优先级 |
| --- | --- | --- | --- |
| 常驻 composer，写完即发，无弹窗 | Memos / jrnl | 页面顶部固定一条输入框 + 「记录」按钮，`Enter` 提交，输入框不清空焦点 | P0 |
| 必填字段只有"内容" | Memos / Traggo / jrnl | 后端只校验 `content` 非空；分类/标签/时间折叠进「补充信息」 | P0 |
| 时间线倒序为主视图 | Memos / ActivityWatch | 主区按 `occurred_at` 倒序的信息流，按日期分组（今天 / 昨天 / 更早） | P0 |
| 归属日期与事件时刻分离 | ActivityWatch | 表字段 `log_date` + `occurred_at`，支持补记 | P0 |
| 日历回溯（点某天看那天） | Memos | 左侧月历，有记录的日期打点，点击过滤当天时间线 | P1 |
| 活动网格（类 GitHub 贡献图） | Dayflow | 页面上方一年 53×7 热力网格，颜色深浅 = 当天条数 | P1 |
| 标签轻量组织 + 筛选 | Memos / Traggo | `tags` 逗号分隔字段 + 顶部标签筛选条（点击即过滤） | P1 |
| 列表 / 日历双视图切换 | Traggo | 主区 Tab 切换「时间线 / 日历」 | P2 |
| 草稿自动保存 | Daily You / 现有 inbox | 复用 `localStorage` draft 模式 | P1 |
| 离线队列 | Daily You / 现有 inbox | 复用 `utils/inboxOfflineQueue.ts` 模式（新建独立 key） | P1 |
| 移动端底部「记录」直达 | Daily You | 复用 `MobileBottomNav.vue` 现有「记录」按钮，指向新页面 | P1 |
| 当日计数轻提示（不叫统计） | Dayflow | 页面顶部一行"今天已记录 N 条"，纯提示不做分析 | P2 |

**明确不借鉴的**：AI 自动分类、摘要生成、情绪分析、图表洞察 —— 用户明确说"暂不考虑其他扩展"。

## 四、方案设计

### 4.1 数据模型

新增 Liquibase changelog `046-create-activity-log.yaml`：

**表 `activity_log`**

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | bigserial | PK | |
| `user_id` | bigint | not null | 用户隔离，对齐全项目约定 |
| `content` | text | not null | 记录正文（唯一必填） |
| `log_date` | date | not null | **归属日期**，用于日历/热力图聚合；默认按 Asia/Shanghai 取 `occurred_at` 的日期 |
| `occurred_at` | timestamp | not null | **事件发生时刻**，默认 `now()`，允许手改以支持补记 |
| `category` | varchar(30) | | 可选：`WORK / STUDY / EXERCISE / FOOD / SOCIAL / REST / OTHER`，默认 `OTHER` |
| `tags` | varchar(500) | | 逗号分隔，对齐 `task_item.tags` 与 `inbox_item.tags` 风格 |
| `source` | varchar(20) | not null | 默认 `WEB`；预留 `MOBILE_WEB / API / AGENT` |
| `pinned` | boolean | not null | 默认 `false`，用于把当天重点钉在顶部（可选，最小实现可砍） |
| `created_at` | timestamp | not null | |
| `updated_at` | timestamp | not null | |

**索引**

- `idx_activity_log_user_date (user_id, log_date DESC)` —— 日历与按天回溯的主查询路径
- `idx_activity_log_user_occurred (user_id, occurred_at DESC)` —— 时间线主查询路径

**设计取舍说明**

- **不做软删除**：需求是"如实记录"，删就是删。若后续要留痕，可加 `deleted_at`，但不进第一版。
- **不做 `status` / `converted_*` 字段**：这是与 `inbox_item` / `quick_note` 的本质分界线，避免被"待整理"语义污染。
- **`category` 与 `tags` 并存**：`category` 是粗粒度单选（便于日后按类过滤），`tags` 是自由多值（满足"如实记录"的弹性）。两者都可为空。
- **`log_date` 用独立字段而非计算列**：因为要支持"今天补记昨天"，归属日期可能与 `occurred_at` 的日期不同。

### 4.2 后端接口

新增模块 `com.personal.assistant.module.activity`（结构对齐 `quicknote` 模块）：

```
module/activity/
├── controller/ActivityLogController.java   @RequestMapping("/api/activity-logs")
├── service/ActivityLogService.java
├── mapper/ActivityLogMapper.java           extends BaseMapper<ActivityLog>
├── entity/ActivityLog.java                 @TableName("activity_log")
└── dto/
    ├── ActivityLogCreateRequest.java       content 必填，其余可选
    ├── ActivityLogUpdateRequest.java
    ├── ActivityLogQuery.java               from/to/keyword/category/tag/page/size
    ├── ActivityLogResponse.java
    └── ActivityDaySummary.java             { date, count }
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/activity-logs` | 新增一条记录 |
| GET | `/api/activity-logs` | 分页列表，支持 `from/to/keyword/category/tag` |

## 五、集成 vs 新建：对比分析与推荐

### 5.1 四个候选方案

- **方案 A：集成进「统一收件箱」**（`inbox_item` 加一种类型，或复用其采集器）
- **方案 B：集成进「每日驾驶舱」**（在 dashboard 页面上加一个活动记录面板）
- **方案 C：复用「开发记录 / 学习记录」**（扩展 `dev_log` 或 `learning_record`）
- **方案 D：新建独立模块 `activity` + 独立页面 `/activity`**（推荐）

### 5.2 多维度对比

| 维度 | A. 集成进收件箱 | B. 集成进仪表盘 | C. 复用开发/学习记录 | D. 新建独立模块 + 页面 |
| --- | --- | --- | --- | --- |
| 语义匹配度 | ❌ 差：inbox 是"待整理素材" | ⚠️ 中：仪表盘是"概览"，不是"记录台" | ❌ 差：领域被限定 | ✅ 好：终态事实记录 |
| 数据模型复用 | 复用 `inbox_item`（但需改造） | 不涉及 | 不可复用（字段不匹配） | 新建 `activity_log` |
| 对现有功能的风险 | 🔴 高：改动 PENDING→CONVERTED 状态机与转换服务 | 🟢 低 | 🟡 中：会污染领域表语义 | 🟢 低：纯新增，零改动 |
| 改动范围 | 后端中 + 前端中 | 后端小 + 前端小 | 后端中 + 前端中 | 后端中 + 前端中（但都是"填空"） |
| 录入摩擦 | 低（已有采集器） | 低 | 中 | 低（复制采集器模式） |
| 按天回溯能力 | ❌ 无 `log_date` 概念，列表按 status 过滤 | ❌ 无 | ❌ 无 | ✅ 原生支持 |
| 长期演进空间 | ❌ 会被"待整理"语义绑架 | ❌ 仪表盘会持续膨胀 | ❌ 领域边界锁死 | ✅ 边界清晰 |
| 菜单可达性（随时记录） | 🟡 需进二级页 | 🟡 需滚到面板 | 🟡 需进二级页 | ✅ 一级菜单直达 |
| 一次性成本 | 中 | 小 | 中 | 中 |

### 5.3 推荐方案：D（新建独立模块 + 独立页面），并做 3 处轻量挂载

**推荐理由**

1. **语义不可兼容是硬约束。** `inbox_item` 和 `quick_note` 的核心生命周期终点都是"被转换成别的业务数据"（`converted_type / converted_id / conversion_params` 就是为此设计的）。而「活动记录」是**终态事实**，写进去就该留着，不存在"待确认"。硬塞进去会导致：PENDING 列表被活动记录永久占满、归档/转换逻辑语义混乱、用户分不清"这条该不该转"。

2. **"按天回溯"是本需求的核心体验，而现有模块没有这个维度。** inbox 是 `status` 维度的流水，quick_note 同理，`habit_checkin` 只有"打卡"没有内容。只有新建表并引入 `log_date` 才能支撑日历与热力图。

3. **零风险增量。** 本项目已积累 45 个 Liquibase changelog、29 个同构模块，新增一个模块是标准的"填空"动作：不改任何现有表、不动任何状态机、不碰鉴权与响应体。这比改造 inbox 的状态机安全得多。

4. **菜单可达性直接决定"随时记录"能否成立。** 用户的核心诉求是"随时记录"。一级菜单 + 移动端底部导航直达，比"进收件箱 → 找 Tab → 找入口"短得多。

5. **成本可控。** 后端：1 张表 + 1 个模块（5 类文件，与 quicknote 同构）+ 少量测试。前端：1 个 api 文件 + 1 个 view + 路由/菜单各 1 行 + `groupRoutes` 1 处。相比改造 inbox，工作量相当但风险低一个量级。

**同时建议的 3 处轻量挂载（让新功能"长在系统里"而不是孤岛）**

| 挂载点 | 改动 | 价值 |
| --- | --- | --- |
| 每日驾驶舱 | `DailyDashboard` 加 `todayActivityCount`，仪表盘加一张卡片 + 移动端"快速记录"按钮改指向 `/activity` | 打开系统第一屏就能记 |
| 全局搜索 | `GlobalSearchMapper` UNION 加入 `activity_log` | 记录可被搜到，不是黑洞 |
| 移动端底部导航 | 「记录」按钮指向 `/activity` | 手机上一步直达 |

**不推荐的补充说明**

- 不建议做成收件箱里的一个 Tab —— 会与"待整理"心智冲突。
- 不建议直接扩展 `dev_log` —— 它是工程语义（commit/分支/技术决策），生活活动塞进去会让两边的字段都变得尴尬。
- 不建议先塞进仪表盘看效果再拆分 —— 仪表盘已经是 8 张卡片的概览页，再加"记录输入区"会同时破坏"概览"与"录入"两种体验。
