# 技术设计文档

## 1. 文档目标

本文档用于指导“个人辅助系统”的后续 AI 辅助开发和人工调整，重点说明页面大致样式、业务模块划分、技术架构拆分、调度模块、股票信息接入、Docker 化部署、本地开发环境、云服务器规格和后续任务拆分。

系统定位不是一次性做成复杂平台，而是先做一个可运行、可扩展、可长期维护的个人系统。第一阶段优先满足个人使用闭环，后续再逐步增强 AI、股票分析、知识库、移动端提醒和自动化能力。

## 2. 设计原则

1. **先可用，后完善**：优先完成核心闭环，不追求一开始模块过度复杂。
2. **前后端分离**：前端负责交互体验，后端负责业务、权限、数据和外部集成。
3. **Java 主体优先**：后端主体使用 Java，便于你理解、调整和维护。
4. **Python 可选增强**：股票数据处理、数据分析、AI 脚本等场景可独立成 Python 服务。
5. **Dockerfile + Compose 部署**：前后端服务通过 Dockerfile 构建镜像，再由 Docker Compose 统一编排。
6. **数据卷持久化**：数据库、上传文件、备份文件和日志必须挂载到 Docker 数据卷或宿主机目录，避免容器删除导致数据丢失。
7. **Liquibase 管理数据库变更**：数据库表结构、初始化数据和版本升级脚本统一通过 Liquibase 管理。
8. **调度能力内置**：提醒、股票采集、备份、日报总结等都通过调度模块统一管理。
9. **适合 AI 继续开发**：模块边界、接口边界、文档和任务拆分要清晰，方便后续让 AI 按模块迭代。

## 3. 总体架构概览

推荐采用“单体后端 + 模块化设计 + 可选 Python 辅助服务”的架构。前期不建议直接上微服务，避免运维复杂度过高。

```text
浏览器 / 手机浏览器
        |
        v
前端应用 Vue / React
        |
        v
Nginx 网关 / 静态资源服务
        |
        v
Java 后端 Spring Boot
        |
        +--> MySQL / PostgreSQL
        +--> Redis 可选
        +--> 文件存储目录
        +--> 调度模块
        +--> 通知 App 接入
        +--> 股票接口接入
        +--> Python 股票分析服务 可选
```

## 4. 推荐技术选型

### 4.1 前端技术

| 分类 | 推荐方案 | 说明 |
| --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript | 对个人项目友好，生态成熟，代码清晰 |
| 构建工具 | Vite | 启动快，配置简单 |
| UI 组件库 | Element Plus | 后台管理类页面开发效率高 |
| 状态管理 | Pinia | 管理登录信息、用户配置、全局字典 |
| 路由 | Vue Router | 管理模块页面入口 |
| 请求库 | Axios | 统一封装请求、错误提示、登录过期处理 |
| 图表 | ECharts | 仪表盘、学习统计、股票趋势展示 |
| Markdown | MdEditorV3 / Milkdown 可选 | 学习总结、工作复盘、笔记编辑 |

如果你更熟 React，也可以改成 React + TypeScript + Ant Design，但从后台系统开发效率看，Vue 3 + Element Plus 更适合快速落地。

### 4.2 后端技术

| 分类 | 推荐方案 | 说明 |
| --- | --- | --- |
| 后端框架 | Spring Boot 3.x | Java 主体开发，便于长期维护 |
| 权限认证 | Spring Security + JWT | 前后端分离常用方案 |
| ORM | MyBatis-Plus | CRUD 效率高，适合个人系统快速开发 |
| 数据库 | PostgreSQL | 已确定，支持 JSON 与全文检索 |
| 缓存 | Redis 可选 | 前期可不用，后续用于验证码、热点数据、任务锁 |
| 定时任务 | Quartz | 支持运行时动态新增/修改/删除任务，任务记录落库，优先于 Spring Scheduler |
| API 文档 | Knife4j / springdoc-openapi | 方便 AI 和自己理解接口 |
| 数据库迁移 | Liquibase | 管理表结构、初始化数据和后续版本升级脚本 |
| 日志 | Logback | 标准日志输出 |
| 对象存储 | 本地目录优先 | 前期存服务器目录，后续可接 MinIO 或云 OSS |

### 4.3 数据库选择

本项目已确定使用 **PostgreSQL**（代码、配置、docker-compose 均已按 PostgreSQL 初始化）。

PostgreSQL 相比 MySQL 的优势：

1. 支持 JSON 字段，适合保存扩展配置、任务参数、股票接口返回摘要。
2. 全文检索能力更灵活，后续知识检索更方便。
3. Quartz JDBC JobStore 对 PostgreSQL 支持完善。
4. Docker 部署成熟，备份恢复方便。

### 4.4 Python 是否需要

股票模块不建议一开始完全依赖 Python。推荐分阶段：

1. **第一阶段**：Java 后端直接保存股票关注项，调用简单股票接口并展示结果。
2. **第二阶段**：如果需要复杂数据处理、指标计算、批量采集、策略分析，再增加 Python 服务。
3. **第三阶段**：Python 服务只负责采集和分析，Java 后端负责账号、页面、调度、结果展示和数据落库。

推荐结论：**主系统用 Java，股票复杂分析用 Python 可选服务。**

## 5. 页面大致样式设计

### 5.1 整体风格

建议采用“个人效率工作台”风格：

- 左侧固定导航栏，右侧内容区。
- 顶部显示搜索框、今日日期、快捷新建、通知状态、用户入口。
- 主色使用低饱和蓝色或青绿色，减少长期使用疲劳。
- 页面留白充足，卡片化展示重点信息。
- 数据密集页面使用表格，记录类页面使用卡片 + 时间线。
- 移动端优先适配查看和快速记录，不追求复杂配置。

## 6. 业务模块拆分

### 6.1 用户与权限模块

负责登录、会话、权限控制和安全配置。

核心能力：

- 用户登录、退出。
- JWT 令牌生成和校验。
- 登录失败记录。
- 会话过期处理。
- 管理功能权限校验。

前期只有你自己使用，可以只设计一个管理员账号，但代码结构仍保留用户表和角色字段，方便后续扩展。

### 6.2 统一事项模块

生活事项、工作事项、学习计划都可以抽象出统一事项能力。

公共字段建议：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| title | 标题 |
| type | 类型：生活、工作、学习 |
| priority | 优先级 |
| status | 状态 |
| planTime | 计划时间 |
| deadline | 截止时间 |
| reminderEnabled | 是否提醒 |
| tags | 标签 |
| remark | 备注 |
| archived | 是否归档 |

不建议所有模块只用一张大表。推荐做法是：

- `task_item` 保存统一事项公共信息。
- `life_item_detail` 保存生活扩展字段。
- `work_item_detail` 保存工作扩展字段。
- `learning_plan` 保存学习计划扩展字段。

### 6.3 生活模块

覆盖生活待办、备忘、习惯、账单提醒、家庭事务等。

第一阶段建议实现：

- 生活事项 CRUD。
- 分类管理。
- 到期提醒。
- 今日待办展示。
- 完成和归档。

后续可以扩展：

- 习惯打卡。
- 周期性事项。
- 家庭资产记录。
- 消费账单提醒。

### 6.4 工作模块

覆盖工作任务、会议记录、问题跟踪、项目复盘。

第一阶段建议实现：

- 工作事项 CRUD。
- 项目字段。
- 截止时间。
- 工作复盘记录。
- 任务状态流转。

后续可以扩展：

- 周报自动生成。
- 会议纪要模板。
- 问题处理知识库。
- 和企业工具链接跳转。

### 6.5 学习与个人成长模块

这是你补充后需要重点设计的模块。

建议拆为四个子模块：

| 子模块 | 说明 |

### 6.6 提醒与通知模块

提醒模块要和外部提醒 App 关联。由于不同提醒 App 的开放能力不同，建议抽象成通知通道。

通知通道类型可预留：

| 通道 | 说明 | 推荐优先级 |
| --- | --- | --- |
| 企业微信机器人 | Webhook 简单稳定 | 高 |
| 钉钉机器人 | Webhook 简单稳定 | 高 |
| Telegram Bot | 个人提醒体验好 | 中 |
| Bark | iOS 推送常用 | 中 |
| Server 酱 | 微信提醒方案 | 中 |
| 邮件 | 通用但提醒感弱 | 低 |

提醒模块核心能力：

- 提醒规则配置。
- 到期提醒扫描。
- 通知通道配置。
- 测试发送。
- 发送日志。
- 失败重试。

### 6.7 股票关注模块

股票模块第一阶段不要做复杂策略，先做“关注列表 + 数据接入预留 + 定时采集日志”。

第一阶段能力：

- 股票关注项维护。
- 股票代码、市场、标签、关注理由。
- 股票接口配置。
- 每日定时采集。
- 采集结果记录。
- 仪表盘展示摘要。

第二阶段能力：

- 行情趋势展示。
- 涨跌幅提醒。
- 财务指标记录。
- 公告信息采集。
- 自定义关注规则。

第三阶段能力：

- Python 指标计算。
- 自定义策略回测。
- AI 总结每日关注股票变化。
- 生成投资观察日报。

### 6.8 调度模块

调度模块是系统自动化能力的核心，建议从一开始就规划。

调度任务类型：

| 类型 | 示例 |
| --- | --- |
| REMINDER_SCAN | 扫描到期提醒 |
| STOCK_COLLECT | 采集股票数据 |
| DATA_BACKUP | 数据备份 |
| DAILY_SUMMARY | 生成每日摘要 |
| LEARNING_REVIEW | 学习复习提醒 |
| SYSTEM_CHECK | 系统健康检查 |

调度任务字段：

| 字段 | 说明 |
| --- | --- |
| jobName | 任务名称 |
| jobType | 任务类型 |
| cronExpression | Cron 表达式 |
| enabled | 是否启用 |
| paramsJson | 参数 JSON |
| retryCount | 失败重试次数 |
| timeoutSeconds | 超时时间 |
| lastRunTime | 上次执行时间 |
| nextRunTime | 下次执行时间 |

执行日志字段：

| 字段 | 说明 |
| --- | --- |
| jobId | 任务 ID |
| startTime | 开始时间 |
| endTime | 结束时间 |
| status | 成功、失败、超时、跳过 |
| outputSummary | 输出摘要 |
| errorMessage | 错误信息 |

前期建议使用 Quartz（JDBC JobStore），任务配置落库并支持运行时动态增删。等需要分布式或可视化调度后台时，再考虑 XXL-JOB。

## 12. 调度模块详细设计

### 12.1 前期实现方案

> 重要修正：不要用 Spring Scheduler 的 `@Scheduled` 实现"页面可配置 Cron 的定时任务"。`@Scheduled` 的表达式在编译期固定，无法在运行时根据数据库配置动态增删任务。需求 8 要求页面创建/启停任意 Cron 任务，因此第一版直接使用 Quartz。

第一阶段建议使用 Quartz（持久化模式 JDBC JobStore）：

- Quartz 表结构由 Liquibase 管理（官方提供 PostgreSQL 建表脚本），与业务 changelog 一起初始化。
- 系统启动后从 `scheduler_job` 表加载启用任务，注册到 Quartz 调度器。
- 页面新增/修改/启停任务时，同步操作 `scheduler_job` 表和 Quartz 调度器（新增/重排/暂停 Trigger）。
- 每个任务按 `job_type` 分发到对应的 JobHandler。
- 执行完成后写入 `scheduler_job_log` 执行日志。
- 失败时按 `retry_count` 配置重试。

任务处理器接口可设计为：

```text
JobHandler
- support(jobType)
- execute(jobContext)
```

Quartz 的 Job 实现统一作为分发器，根据 `job_type` 找到对应 JobHandler 执行，避免为每种任务写一个 Quartz Job 类。

处理器示例：

| 处理器 | 说明 |
| --- | --- |
| ReminderScanJobHandler | 扫描到期提醒 |
| StockCollectJobHandler | 采集股票数据 |
| DataBackupJobHandler | 执行数据备份 |
| LearningReviewJobHandler | 生成学习复习提醒 |
| SystemHealthCheckJobHandler | 系统健康检查 |

### 12.2 后续升级方案

当任务需要分布式执行、可视化调度后台、跨多机器部署时，再升级为 XXL-JOB。

升级条件：

- 需要独立的可视化调度管理后台。
- 需要多机器分布式执行同一批任务。
- 需要更完整的任务失败告警和报表。
- 单机 Quartz 已无法满足任务规模。

## 15. 安全设计

### 15.1 登录安全

- 密码必须哈希存储，不能明文保存。
- 登录失败需要记录失败次数和 IP。
- JWT 设置合理过期时间。
- 管理类接口必须校验登录态。

### 15.2 敏感配置安全

敏感配置包括：

- 通知 App Webhook。
- 股票接口 Key。
- 数据库密码。
- JWT 密钥。
- 备份文件。

处理原则：

- `.env` 文件不提交到代码仓库。
- 页面展示时脱敏。
- 数据库存储敏感字段时加密。
- 备份文件限制访问权限。

### 15.3 服务器安全

- 只开放必要端口。
- SSH 使用强密码或密钥登录。
- 关闭数据库公网访问。
- 配置 HTTPS。
- 定期更新系统补丁。
- 备份文件不要只放在同一台服务器。

## 20. 股票自选股云图第一版设计补充（2026-07-01）

### 20.1 定位

- 点击股票方块打开详情抽屉。

### 20.5 后续演进

- 接入真实行情源后，由采集任务标准化更新 `latest_price`、`change_percent`、`market_value`、`quote_time` 等字段。
- 第二版可扩展全市场云图、行业指数、成交额统计、涨跌分布和分时曲线。
- 如果云图布局复杂度继续提升，可引入 ECharts Treemap 取代当前 CSS 原生布局。
### 20.6 实时行情刷新第一版补充

股票模块在自选股云图基础上增加实时行情刷新入口：

```text
POST /api/stocks/quotes/refresh?market=CN&enabledOnly=true
```

第一版行为：

- 查询当前用户关注股票。
- 支持按市场过滤，默认可只刷新启用项。
- A 股通过内置行情源获取最新价、涨跌幅、市值和刷新时间。
- 成功后回写 `stock_watch_item` 标准行情字段。
- 每只股票都会写入 `stock_collection_result`，用于追踪刷新成功或失败。
- 前端“大盘云图”页签通过“刷新实时行情”按钮触发。

限制和演进：

- 第一版只内置 A 股刷新逻辑。
- 港股、美股以及更稳定的生产行情应通过后续供应商配置或独立行情 Provider 接入。
- 如果后续接入付费行情源，建议将行情 Provider 抽象为独立接口，并支持供应商限流、重试、熔断和字段映射配置。
### 20.7 股票行情第二版设计补充

第二版目标是让实时行情从“手动刷新”升级为“可调度、可追踪、状态可见”。

新增接口：

```text
GET /api/stocks/quotes/status?market=CN&enabledOnly=true
```

返回：

- 当前关注股票数量。
- 已有行情和缺失行情数量。
- 最近一次行情时间。
- 最近一次采集/刷新时间。
- 最近采集成功和失败数量。
- 最近失败明细。

调度集成：

- `STOCK_COLLECT` 任务调用 `StockService.refreshEnabledQuotesForScheduler()`。
- 调度刷新和手动刷新复用同一套实时行情逻辑。
- 每只股票的成功/失败仍写入 `stock_collection_result`。

前端展示：

- 大盘云图顶部展示行情状态条。
- 关注列表顶部展示关注数、已有行情数、缺失行情数、上次行情时间和上次刷新时间。
- 刷新实时行情后自动刷新云图、关注列表和状态。

后续设计方向：

- 调度任务配置支持市场、标签、刷新范围和刷新频率。
- 行情 Provider 抽象化，支持 A 股、港股、美股多供应商切换。
- 引入接口限流、失败重试和失败告警。

## 22. 金价关注模块第一版设计补充（2026-07-02）

### 22.1 模块定位

金价关注模块用于集中跟踪个人关心的黄金价格，包括伦敦金、国内金价、银行/平台报价金以及各品牌首饰金价。第一版重点是打通数据模型、接口配置、手动维护、采集结果和页面展示，后续再根据稳定数据源扩展具体 Provider。

### 22.2 数据模型

新增三张表：

| 表名 | 说明 |
| --- | --- |
| `gold_watch_item` | 金价关注项，保存类型、品牌/渠道、单位、最新价、涨跌、高低开收、买卖价、来源和启用状态 |
| `gold_api_config` | 金价接口配置，保存接口名称、用途、地址、认证方式、加密 API Key、限流和测试结果 |
| `gold_collection_result` | 金价采集结果，记录关注项、接口配置、成功状态、摘要、原始数据、错误信息和采集时间 |

`gold_watch_item.gold_type` 当前支持：

- `LONDON_GOLD`：伦敦金。
- `DOMESTIC_GOLD`：国内金价。
- `BRAND_JEWELRY`：品牌首饰金价。
- `PLATFORM_GOLD`：银行/平台报价金，例如截图中的同花顺黄金、银行渠道报价金。

### 22.3 后端接口

新增后端模块：`com.personal.assistant.module.gold`。

核心接口：

```text
GET  /api/gold/watch-items
POST /api/gold/watch-items
PUT  /api/gold/watch-items/{id}
PATCH /api/gold/watch-items/{id}/enabled
GET  /api/gold/api-configs
POST /api/gold/api-configs
PUT  /api/gold/api-configs/{id}
POST /api/gold/api-configs/{id}/test
GET  /api/gold/collection-results
POST /api/gold/quotes/refresh
GET  /api/gold/quotes/status
POST /api/gold/collect
```

### 22.4 配置化采集策略

第一版不硬编码不稳定品牌页面爬虫，而是支持配置接口地址和认证方式。接口地址支持占位符：

```text
{type} / {goldType} / {brand} / {unit}
```

返回 JSON 会宽松识别常见字段：

| 标准字段 | 可识别来源字段示例 |
| --- | --- |
| 最新价 | `latestPrice`, `price`, `last`, `close`, `current`, `value`, `sellPrice` |
| 涨跌额 | `changeAmount`, `change`, `riseFall`, `diff` |
| 涨跌幅 | `changePercent`, `percent`, `pctChange`, `chgPct`, `riseFallPercent` |
| 最高/最低/今开/昨收 | `high`, `low`, `open`, `prevClose`, `yesterdayClose`, `lastClose` |
| 买价/卖价 | `buyPrice`, `buy`, `bid`, `sellPrice`, `sell`, `ask` |
| 行情时间 | `quoteTime`, `time`, `timestamp`, `updatedAt` |

### 22.5 调度集成

新增调度处理器 `GoldCollectHandler`，任务类型为：

```text
GOLD_COLLECT
```

调度执行时调用 `GoldService.refreshEnabledQuotesForScheduler()`，刷新启用金价关注项，并写入 `gold_collection_result`。

### 22.6 前端页面

新增页面：`/gold`，菜单名称为“金价关注”。页面包含：

- 金价看板：以卡片展示最新价、涨跌、高低开收、买卖价和行情时间。
- 关注列表：管理伦敦金、国内金价、品牌首饰金价、银行/平台报价金。
- 接口配置：维护金价数据源、认证方式、API Key 和接口测试。
- 采集结果：查看每次刷新成功/失败摘要。

### 22.7 后续演进

- 接入稳定供应商后，可新增专用 Provider，替代通用 JSON 字段识别。
- 对品牌首饰金价可扩展为多品牌批量导入和历史走势。
- 对伦敦金/平台报价金可扩展分时、日 K、周 K、月 K 曲线。
