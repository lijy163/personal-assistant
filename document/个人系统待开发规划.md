# 个人系统待开发规划

## 1. 文档说明

### 1.1 建设目标

在现有个人助手系统基础上，逐步建设以下能力：

1. 接入 DeepSeek，提供统一、可控的数据整理与分析能力。
2. 建立个人账单中心，统一管理支付宝、微信和银行卡流水。
3. 自动沉淀 Codex 开发过程中的精炼技术记录。
4. 扩展 A 股模块，增加个股与板块资金流向图。
5. 提升移动端、快捷录入、统一搜索和主动提醒体验。

### 1.2 当前系统基础

当前系统采用模块化单体架构，主要技术包括：

- 后端：Java 17、Spring Boot、Spring Security、MyBatis-Plus、Liquibase、Quartz。
- 前端：Vue 3、TypeScript、Element Plus、Vite。
- 数据库：PostgreSQL。
- 部署：Docker Compose、Nginx。
- 已有模块：认证、快捷记录、任务、学习、提醒、调度、A 股、黄金、备份和系统管理。
- 可复用能力：JWT 鉴权、用户数据隔离、AES-GCM 密钥加密、外部 HTTP API、定时调度、Markdown 内容和数据备份。

当前尚未建设通用 AI 网关、账单导入框架、开发知识库、统一全文检索、PWA 和资金流历史数据。

## 2. 建设原则

1. 保持模块化单体架构，暂不拆分微服务。
2. 原始数据与加工结果分开保存，禁止 AI 结果覆盖原始数据。
3. 确定性规则优先，AI 只处理难以规则化的内容。
4. 所有自动处理结果必须可追溯、可重新执行、可人工修正。
5. 密钥、令牌和敏感配置不得明文入库。
6. 不采用模拟登录、抓包、自动点击等高风险方式采集金融数据。
7. 新增外部数据源必须通过适配器隔离，避免业务代码绑定单一供应商。
8. 优先建设小而完整的闭环，再增加复杂分析功能。

## 3. DeepSeek 智能处理模块

### 3.1 可行性结论

可以接入。现有后端已经具备外部 HTTP 调用和密钥加密能力，首期可直接调用 DeepSeek 的兼容接口，无须引入重型 AI 框架。

### 3.2 首期使用场景

- 将快捷记录识别为任务、提醒、学习笔记或普通记录。
- 对账单商户和交易摘要进行辅助分类。
- 生成消费月报、工作周报和学习总结。
- 对 Codex 开发记录进行压缩、规范化和自动打标签。
- 将文本或表格整理为系统约定的结构化 JSON。

### 3.3 后端设计

新增 `ai` 模块，建议包含：

- `AiGatewayService`：统一模型调用入口。
- `AiProvider`：隔离 DeepSeek 及后续其他模型供应商。
- `AiTaskService`：管理异步任务、状态和重试。
- `PromptTemplateService`：维护不同业务场景的提示词模板。
- `AiOutputValidator`：校验模型返回的结构化结果。

建议新增数据表：

| 数据表 | 用途 |
| --- | --- |
| `ai_provider_config` | 模型地址、模型名称、加密 API Key、限流配置 |
| `ai_prompt_template` | 业务场景、模板版本、结构化输出约束 |
| `ai_task` | 任务类型、状态、输入摘要、输出、耗时、失败原因 |
| `ai_usage_log` | 模型、Token 用量、调用时间和业务来源 |

### 3.4 安全要求

- 前端不得直接调用模型或持有 API Key。
- 身份证号、银行卡号、手机号、交易单号等信息发送前必须脱敏。
- 默认不发送完整源码、完整 Git Diff、环境变量和终端原始日志。
- 设置单次输入长度、每日额度、超时、重试次数和并发限制。
- 保存提示词版本、模型名称和业务记录 ID，保证结果可追溯。
- 具体模型名称、价格与限流以实际 DeepSeek 控制台为准。

### 3.5 验收标准

- 可在系统内配置并测试 DeepSeek。
- 可提交一种结构化处理任务并查询执行状态。
- 超时、限流和格式错误有明确失败原因。
- API Key 加密保存，查询接口只返回脱敏值。
- AI 结果支持人工修改，原始数据不受影响。

## 4. 个人账单中心

### 4.1 可行性结论

可以建设，但首期采用“官方账单文件导出后导入系统”，不承诺直接读取个人支付宝、微信或银行卡账户。

支付宝和微信开放平台主要服务商户交易，通常不能用于读取普通用户的完整个人消费流水。银行能力也受银行、地区和授权方式限制。

### 4.2 首期范围

- 支持支付宝 CSV/XLSX 账单导入。
- 支持微信 CSV/XLSX 账单导入。
- 支持主流银行卡 CSV/XLSX 账单导入。
- PDF 解析或 OCR 仅作为无结构化账单时的兜底能力。
- 支持收入、支出、退款、转账、信用卡还款和账户内部转移。
- 支持重复流水识别和导入预览。
- 支持规则分类、AI 辅助分类和人工确认。

### 4.3 数据模型

新增 `finance` 模块，建议包含：

| 数据表 | 用途 |
| --- | --- |
| `finance_account` | 支付宝、微信、银行卡、现金等资金账户 |
| `finance_import_batch` | 文件来源、摘要、导入结果和错误信息 |
| `finance_raw_transaction` | 保留导入文件中的原始交易字段 |
| `finance_transaction` | 统一后的标准交易记录 |
| `finance_category` | 收支分类及层级 |
| `finance_category_rule` | 商户、关键词和金额等自动分类规则 |
| `finance_reconciliation` | 退款、还款、账户内部转移等关联关系 |

### 4.4 导入流程

```text
上传账单
→ 校验文件类型、大小和摘要
→ 识别支付宝、微信或银行格式
→ 平台解析器读取原始字段
→ 映射统一交易结构
→ 根据交易指纹去重
→ 执行本地分类规则
→ DeepSeek 辅助处理未识别项目
→ 用户确认低置信度记录
→ 事务入库并生成导入报告
```

交易指纹可由“账户、平台交易号、交易时间、金额、方向和商户”等字段组合生成。导入过程必须具备事务边界，失败时不能留下半批数据。

### 4.5 后续能力

- 月度和年度收支趋势。
- 分类预算与超支提醒。
- 订阅服务和固定支出识别。
- 异常大额、重复扣款和消费突增提醒。
- 从指定邮箱读取银行账单附件。
- 在明确支持个人授权且满足合规要求时，再评估金融数据聚合服务。

### 4.6 禁止事项

- 不保存支付密码、银行卡密码或短信验证码。
- 不使用爬虫模拟支付宝、微信或网银登录。
- 不通过手机自动点击或抓包绕过平台限制。
- 不把完整账单无差别发送给大模型。

## 5. Codex 开发总结沉淀

### 5.1 建设目标

Codex 完成开发任务后，自动生成一份短小、结构统一、可以检索的开发记录，并安全推送至个人系统。

### 5.2 模块边界

新增独立 `devlog` 模块，不直接写入现有 `learning_summary`。学习总结与学习计划、统计周期绑定，而开发日志需要关联代码仓库、分支和提交，两者领域语义不同。

统一搜索页面后续可以同时检索开发记录和学习总结。

### 5.3 推荐流程

```text
Codex 完成任务
→ 本地脚本收集用户目标、变更文件、Diff 统计和验证结果
→ 按固定模板生成精炼 JSON/Markdown
→ 调用 POST /api/devlogs/ingest
→ 服务端根据任务指纹幂等入库
→ 可选调用 DeepSeek 压缩和打标签
→ 在系统中检索、回顾和关联项目
```

### 5.4 开发记录字段

- 标题。
- 项目名称和仓库路径标识。
- 分支和提交号。
- 原始任务目标。
- 核心修改。
- 关键技术决策及原因。
- 问题、根因和解决方式。
- 验证方式和结果。
- 标签、来源和发生时间。
- 精炼 Markdown 正文。

### 5.5 推送鉴权

自动化推送不使用长期网页登录 JWT。新增 Personal Access Token：

- 令牌只授予 `devlog:write` 权限。
- 数据库只保存 Token 哈希。
- 支持名称、创建时间、最近使用时间、过期时间和撤销状态。
- 可针对不同电脑或工具创建独立 Token。
- 接口需限制请求大小并记录审计信息。

### 5.6 触发方式

按推荐顺序实施：

1. Codex 固定总结提示词加本地推送命令，便于人工确认。
2. Git `post-commit` Hook，只处理已提交的开发任务。
3. Kiro `Stop` 或 `PostTaskExec` Hook，作为补充自动化入口。

### 5.7 内容边界

默认不上传：

- 完整源代码和完整 Diff。
- `.env`、API Key、密码和 Token。
- 客户数据及生产数据库内容。
- 未经清洗的终端日志。

## 6. A 股资金流向图

### 6.1 可行性结论

可以实现。现有 A 股模块已经具备自选股、A 股代码到 `secid` 的转换、东方财富实时行情请求、定时采集和采集结果记录能力，可以复用这些基础。

当前模块只有最新价、涨跌幅、市值、行业和行情时间，没有资金流字段，也没有资金流历史时序。因此需要新增独立的资金流快照表，不能只把最新值写回 `stock_watch_item`。

### 6.2 指标口径

首期建议采集并展示：

- 主力净流入额和净占比。
- 超大单净流入额和净占比。
- 大单净流入额和净占比。
- 中单净流入额和净占比。
- 小单净流入额和净占比。
- 当日涨跌幅、最新价和成交额。
- 数据时间和数据来源。

资金流属于根据成交单规模计算的行情指标，不等同于真实机构账户资金变化。页面必须显示供应商、更新时间和指标口径说明，不能将其描述为确定的买卖结论。

### 6.3 MVP 展示方案

在现有 A 股页面新增“资金流向”标签页，包含：

1. 总览卡片：自选股主力净流入合计、流入股票数、流出股票数、更新时间。
2. 净流入排行：横向柱状图展示自选股主力净流入和净流出排名。
3. 单股趋势：折线图展示选中股票当日或近 N 日主力净流入变化。
4. 单型分布：堆叠柱状图展示超大单、大单、中单和小单资金结构。
5. 明细表格：展示各项金额、占比、涨跌幅和采集时间。

前端当前没有图表库，建议引入 ECharts，并封装通用图表组件，避免图表初始化、缩放和销毁逻辑散落在业务页面。

### 6.4 二期展示方案

- 行业板块资金流入热力图。
- 概念板块资金流入热力图。
- 沪深市场整体资金流趋势。
- 个股近 5 日、10 日和 20 日累计资金流。
- 资金流与涨跌幅背离提示。
- 自选股资金流异常提醒。

行业与概念板块不能长期依赖当前用户手填的 `industry` 字段。二期应建立供应商板块代码、板块名称和成分股关系。

北向资金等跨境资金指标受数据披露规则和供应商口径影响，不纳入首期交付承诺。

### 6.5 数据模型

建议新增：

| 数据表 | 用途 |
| --- | --- |
| `stock_fund_flow_snapshot` | 保存个股分钟级或日级资金流快照 |
| `stock_sector` | 二期保存行业或概念板块主数据 |
| `stock_sector_member` | 二期保存板块与股票关系 |
| `stock_sector_fund_flow_snapshot` | 二期保存板块资金流快照 |

`stock_fund_flow_snapshot` 建议字段：

- `id`、`user_id`、`watch_item_id`。
- `stock_code`、`market`。
- `main_net_inflow`、`main_net_ratio`。
- `super_large_net_inflow`、`super_large_net_ratio`。
- `large_net_inflow`、`large_net_ratio`。
- `medium_net_inflow`、`medium_net_ratio`。
- `small_net_inflow`、`small_net_ratio`。
- `latest_price`、`change_percent`、`turnover_amount`。
- `provider`、`period_type`、`quote_time`、`collected_at`。

建议以 `user_id + watch_item_id + provider + period_type + quote_time` 建立唯一约束，防止调度重复写入。

### 6.6 后端接口

建议新增：

| 接口 | 用途 |
| --- | --- |
| `POST /api/stocks/fund-flow/refresh` | 刷新启用自选股资金流 |
| `GET /api/stocks/fund-flow/overview` | 查询资金流总览与排行 |
| `GET /api/stocks/{watchId}/fund-flow/latest` | 查询单股最新资金流 |
| `GET /api/stocks/{watchId}/fund-flow/trend` | 查询单股时序趋势 |
| `GET /api/stocks/fund-flow/status` | 查询覆盖率、更新时间和失败信息 |

新增 `StockFundFlowProvider` 接口和供应商实现。Service 只依赖 Provider，不直接拼装供应商地址，以便公开接口变化后切换到合规商业 API。

### 6.7 数据来源与风险

MVP 可沿用当前东方财富数据能力验证功能，但需注意：

- 公开页面接口可能变更字段、限流或增加访问限制。
- 字段含义和单位必须通过样本校验，不允许仅凭字段编号猜测。
- 保存供应商名称和采集时间，避免混合不同口径。
- 设置超时、限速、失败重试和熔断，不能高频无控制调用。
- 若系统长期使用或对准确性要求提高，应切换到有明确授权和服务保障的数据供应商。

### 6.8 调度策略

首期建议：

- 交易时间内每 5～15 分钟刷新启用自选股。
- 收盘后执行一次日终快照。
- 非交易时间不进行分钟级采集。
- 单次刷新限制自选股数量，按供应商限流分批执行。
- 复用 Quartz，但使用独立的资金流任务类型，不与普通行情刷新混为同一任务。

### 6.9 验收标准

- 可手动刷新全部启用的 A 股自选股资金流。
- 可显示刷新成功数、失败数、覆盖率和最后更新时间。
- 可查看主力净流入排行和单股资金流趋势。
- 相同时间点重复刷新不会生成重复快照。
- 接口异常时保留上一批有效数据，并向用户显示失败原因。
- 金额单位、正负方向、占比和供应商口径经过样本核对。
- 非 A 股代码有明确提示，不产生无意义数据。

## 7. 便携能力规划

### 7.1 每日驾驶舱

集中展示今日任务、提醒、待确认账单、自选股异动、开发进展和学习目标。

### 7.2 统一收件箱

提供一句话快速录入，系统通过规则和 AI 判断内容属于任务、提醒、消费、学习笔记还是普通记录，再由用户确认。

### 7.3 全局搜索

统一搜索快捷记录、任务、学习总结、开发日志、账单和股票备注。首期使用 PostgreSQL 全文检索，数据量或语义检索需求明确后再评估向量库。

### 7.4 PWA 移动端

- 安装到手机桌面。
- 移动端响应式导航。
- 快捷记录和账单上传。
- 关键提醒推送。
- 对可缓存页面提供有限离线访问。

### 7.5 自动报告与主动提醒

- 每周生成工作、学习和任务总结。
- 每月生成消费分析和预算提醒。
- 提醒订阅续费、异常消费和重复扣款。
- 提醒长时间未完成的任务。
- 提醒自选股资金流异常变化，但不输出确定性投资建议。

### 7.6 数据可携带

- 支持 Markdown、JSON 和 CSV 导出。
- 备份文件包含版本信息和恢复校验。
- 用户可独立导出账单、开发日志和学习记录。
- 保留现有 PostgreSQL 备份恢复能力。

A 股资金流功能可在 DeepSeek 之前独立开发；它本身不依赖大模型。若当前最关注股票模块，也可以将 A 股资金流 MVP 提升为第一优先级。

## 10. 交付前统一检查

每个模块交付前必须确认：

- 数据表具备用户隔离、必要索引和唯一约束。
- 后端写操作具备事务边界。
- 外部调用具备超时、限流、失败记录和用户反馈。
- 敏感信息已加密或脱敏。
- 数据来源、更新时间和指标口径可见。
- 自动化操作支持关闭、撤销或人工修正。
- 页面在桌面端和移动端均可正常操作。
- 备份与导出覆盖新增核心数据。
